DUPLICATE INVOICE — EXCEPTION RESOLUTION
STANDARD OPERATING PROCEDURE (SOP)
Version 1.0

================================================================================
PURPOSE
================================================================================

This SOP defines how the agent resolves a DUPLICATE INVOICE exception, where a
supplier invoice number already exists for the same vendor in SAP S/4HANA. It
applies after three-way-match classification has identified the exception as a
potential duplicate. The goal is to prevent double payment while not rejecting
legitimate resubmissions or corrective invoices.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in RFC 2119.

================================================================================
SCOPE
================================================================================

Process Type: duplicate_invoice
SAP Modules:  FI-AP (Accounts Payable)
SAP Service:  API_SUPPLIERINVOICE_PROCESS_SRV
Entities:     A_SupplierInvoice

================================================================================
PRECONDITIONS
================================================================================

Before execution, the following MUST be true:

1. The SAP MCP Server is reachable for reads.
2. The case payload contains the supplier invoice number, vendor, and fiscal
   year.
3. The agent has NO memory of prior runs — each execution is stateless.

================================================================================
STEP 1: GATHER DATA
================================================================================

1.1  The agent MUST retrieve the incoming invoice header (A_SupplierInvoice):
     vendor, invoice number, amount, currency, invoice date, and line items.
1.2  The agent MUST query existing invoices for the same vendor and invoice
     number to locate the suspected original, including its payment status.

================================================================================
STEP 2: COMPARE AGAINST THE ORIGINAL
================================================================================

2.1  The agent MUST compare the incoming invoice with the existing one on:
     amount, invoice date, and line items.
2.2  The agent MUST compute the amount difference using the calculator tool:
       amount_difference = |incoming_amount - original_amount|

================================================================================
STEP 3: APPLY RESOLUTION LOGIC
================================================================================

3.1  IF the incoming invoice matches the original on amount (within
     ${{DUPLICATE_MATCH_WINDOW_USD}}), date, and line items:
     - The agent MUST treat it as a TRUE DUPLICATE. The agent MUST NOT post it.
     - The agent MUST reject the invoice and notify the vendor via
       {{CONTACT_AP_TEAM}}, referencing the original invoice/document number.
     - The agent MUST update case state to 'complete' with disposition
       "rejected_duplicate".

3.2  IF the amount difference exceeds ${{DUPLICATE_MATCH_WINDOW_USD}} OR line items
     differ:
     - The invoice MAY be a partial, corrective, or resubmitted invoice. The
       agent MUST escalate to {{CONTACT_AP_TEAM}} with both invoices' numbers,
       amounts, dates, and the differences identified.
     - The agent MUST update case state to "awaiting_human_input" and STOP.

3.3  The agent cannot read payment status — the service exposes
     SupplierInvoiceStatus and PaymentBlockingReason, not a cleared/paid flag.
     Where the original is posted and carries no payment block, the agent MUST
     treat double payment as possible, say so explicitly in the notification to
     {{CONTACT_FINANCE_APPROVALS}}, and state that payment status needs human
     confirmation. The agent MUST NOT assert that the original was or was not
     paid.

3.4  The agent MUST NOT post a suspected duplicate without human confirmation.

================================================================================
STEP 4: CLOSE CASE
================================================================================

4.1  For a confirmed true duplicate, the agent MUST close the case with the
     rejection recorded.
4.2  For an escalated corrective/partial invoice, the agent MUST wait for the AP
     team's decision before any posting.
4.3  IF a write fails, the agent MUST set the case to 'error', notify
     {{CONTACT_AP_TEAM}}, and STOP.

================================================================================
ESCALATION RULES
================================================================================

| Trigger                                   | Action                              |
|-------------------------------------------|-------------------------------------|
| True duplicate                            | Reject + notify {{CONTACT_AP_TEAM}} |
| Amount/line-item difference               | Escalate {{CONTACT_AP_TEAM}}        |
| Original already paid (double-pay risk)   | Flag {{CONTACT_FINANCE_APPROVALS}}  |

================================================================================
CONTACTS
================================================================================

- AP Team:           {{CONTACT_AP_TEAM}}
- Finance Approvals: {{CONTACT_FINANCE_APPROVALS}}

================================================================================
TOLERANCES (CONFIGURABLE — DECLARED IN skills/finance_ap/config.json)
================================================================================

|---------------------------------|--------------------------------|
| Duplicate-match window (USD)    | {{DUPLICATE_MATCH_WINDOW_USD}} |
